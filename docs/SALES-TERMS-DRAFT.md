# yutori POS 販売にあたっての免責事項・条件整理（ドラフト）

> **本書の位置づけ** — 契約書のたたき台と論点整理です。法的助言ではありません。実際に締結する契約書・利用規約は、弁護士のレビューを受けてください。特に「責任の上限」「免責の範囲」は、書き方によって無効と判断される条項があります。

---

## 0. 前提としている販売形態

| 項目 | 内容 |
|------|------|
| 対価 | 買い切り（初期費用のみ）。**インフラ維持費 約100か月分相当を含む価格設定** |
| 追加対応 | 検収期間経過後の改修・機能追加は都度見積の別料金 |
| 検収 | 納品後**1か月をテスト期間**とし、その間の不具合・修正に無償対応 |
| ソフトウェア | 提供者が著作権を保持し、顧客には利用を許諾（譲渡しない） |
| インフラ | Supabase / Vercel / Google Apps Script は**提供者のアカウントで運用**。維持費は提供者負担（他用途と共用のため実質的な追加負担なし） |
| 環境分離 | **顧客ごとに Supabase プロジェクトを分ける** |
| 決済 | Square は顧客自身が Square 社と契約（提供者は連携のみ） |
| 想定顧客 | 事業者（飲食・シーシャラウンジ等）。消費者向け販売ではない |

## 1. 契約書で必ず決めるべきこと（免責より先に）

この販売形態には、免責条項では処理できない**構造的な論点**があります。ここを曖昧にしたまま売ると、後で必ず揉めます。

### 1-1. 運用期間の終わり方だけは決めておく

維持費は価格に約100か月分を織り込み済みで、かつ他用途と共用のサーバーのため、**費用負担の取り決めは不要**という整理です。それでも、以下の1点だけは契約書に入れてください。費用の話ではなく、**やめ方**の話です。

- **提供者が◯か月前の通知で運用を終了できる**旨（廃業・事業方針の変更・第三者サービスの提供終了に備える）

これが無いと、口頭の「買い切り」が「無期限の運用義務」と解釈される余地が残ります。1文入れておけば足ります。

> 参考: Supabase の無料プランは、1組織あたりに作成できるプロジェクト数に上限があります。顧客が増えると有料プランが必要になるため、**何件までなら現行コストで収まるか**は事前に確認しておくと安全です。

### 1-2. 提供者がいなくなった場合の備え

インフラが提供者名義のため、提供者が廃業・連絡不能になると顧客は売上データを取り出せなくなります。顧客から必ず質問される点なので、答えを用意しておいてください。

- 日次の売上はスプレッドシート（顧客側で閲覧可能）に出ているため、**日次集計は顧客の手元に残る**
- ただし**会計明細・経費・商品マスタは顧客の手元に無い** — 契約終了時に渡す手段を決めておく（3-4 参照）

### 1-3. サポート範囲の線引き

「どこまでが無償で、どこからが別料金か」を表にして契約書に添付してください。

| 区分 | 例 | 費用 |
|------|-----|------|
| 無償 | **納品後1か月のテスト期間中**に判明した不具合・修正 | 含む |
| 無償（運用） | サーバー障害の一次対応 | 含む |
| 有償 | テスト期間経過後の不具合修正、機能追加、画面変更 | 都度見積 |
| 有償 | 商品マスタの一括登録代行、顧客の操作ミスに起因するデータ復旧 | 都度見積 |
| 対象外 | 端末（タブレット・スマホ）の故障、店舗のネット回線 | 顧客負担 |

- **応答時間**（例: 平日10-18時、翌営業日以内に一次回答）を明記する
- 24時間365日の即応は約束しない。営業時間が深夜帯の業態なので、**深夜の障害対応を約束するかどうか**は特に慎重に

## 2. 免責事項ドラフト（条文案）

以下は条文のたたき台です。番号・文言は契約書の体裁に合わせて調整してください。

### 第◯条（保証の範囲）

1. 提供者は、本システムが**納品時点の仕様書に実質的に適合すること**を保証します。
2. 提供者は、本システムが顧客の特定の目的に適合すること、顧客の業務要件のすべてを満たすこと、および**中断なく、エラーなく稼働することを保証しません**。
3. 本システムは現状有姿（AS IS）で提供され、前項に定めるほか、明示・黙示を問わずいかなる保証も行いません。

### 第◯条（テスト期間と不具合対応）

1. 納品日から **1か月間**をテスト期間とし、顧客はこの期間内に本システムの動作を確認するものとします。
2. 提供者は、テスト期間中に顧客から通知された仕様との不適合について、**無償で修正**します。
3. **テスト期間の経過後**に判明した不具合の修正、および仕様の変更・機能追加は、別途見積のうえ**有償**で対応します。
4. 顧客が本システムを改変した場合、または提供者の指定しない環境で使用した場合に生じた不具合は、第2項の対象外とします。

### 第◯条（PayPay での支払い）

1. PayPay での支払いは、店頭に掲示する QR コードによりお客様が直接 PayPay へ支払う方式です。提供者は決済の当事者ではありません。
2. 本システムへの記録は、**顧客が PayPay の支払い完了を確認したうえで**行うものとし、**支払いの実体を伴わない記録（空会計）を行ってはなりません**。
3. 誤って記録した場合、顧客は**会計から7日以内に**当該会計を取り消すものとします。7日を経過すると本システム上では取り消せません。
4. 空会計またはその放置に起因して生じた損害について、提供者は責任を負いません。

> 補足: PayPay の取引履歴と本システムの記録を突き合わせれば、空会計は検出できます。日次の締め作業に組み込むことを推奨します。

### 第◯条（外部サービスへの依存）

1. 本システムは、以下の第三者サービスに依存して稼働します。

   - Supabase（データベース・リアルタイム同期）
   - Vercel（アプリケーションの配信）
   - Square（キャッシュレス決済）
   - Google Apps Script / Google スプレッドシート（売上の書き出し）
   - Open-Meteo（日報の天気取得）

2. これらのサービスの**障害・仕様変更・値上げ・提供終了**に起因して本システムが利用できない場合、またはこれに対応するための改修が必要となった場合、提供者は責任を負いません。改修が必要な場合の費用負担は別途協議します。
3. Square による決済処理そのものは Square 社と顧客との契約に基づくものであり、**決済の成否・入金・手数料について提供者は責任を負いません**。

### 第◯条（データの取扱いと消失）

1. 提供者は、**本システムに記録されたデータの完全性・保存・復旧を保証しません**。
2. データが消失した場合、顧客は次の方法により記録を再構成するものとし、提供者はこれに必要な範囲で協力します。

   - **現金・カード決済** — Square の取引履歴を参照し、本システムへ再入力する
   - **PayPay での支払い** — PayPay 加盟店管理画面（PayPay for Business）の取引履歴を参照し、本システムへ再入力する
   - **日次の売上集計** — 同期済みの Google スプレッドシートを参照する

3. 前項の方法によっても、**次の情報は復元できません**。顧客はこれを了承のうえ本システムを利用するものとします。

   - **オーダーの明細**（商品・数量・単価。決済事業者には合計金額のみが残ります）
   - **経費・引継ぎメモ・商品マスタ・フロアレイアウト**
   - 未同期の期間（前回のスプレッドシート同期以降）の集計

4. 顧客の操作（会計取消、商品・カテゴリの削除等）によるデータの消失について、提供者は責任を負いません。
5. 顧客は、**スプレッドシート同期を定期的に実行**し、売上記録を顧客自身の管理下にも保持するものとします。

### 第◯条（通信環境・端末）

1. 本システムはインターネット接続を前提とします。**オフライン環境での動作は保証しません**。
2. 通信が不安定な状態で操作した場合、入力内容が保存されないことがあります。
3. 動作対象は、提供者が指定する OS・ブラウザの最新版とします。それ以外の環境での不具合は保証の対象外です。
4. 端末（タブレット・スマートフォン）の調達・管理・故障対応は顧客の責任とします。

### 第◯条（会計・税務）

1. 本システムが算出する金額・消費税額・集計値は、**会計処理および税務申告のための参考値**です。
2. 本システムは**適格請求書（インボイス）の発行機能を有しません**。適格請求書の交付が必要な場合、顧客は別途対応するものとします。
3. 本システムは、電子帳簿保存法上の**優良な電子帳簿等の要件充足を保証しません**。帳簿書類の保存要件の充足は顧客の責任とします。
4. 消費税額の端数処理方法は納品時の仕様のとおりとし、税制改正への対応は有償の改修とします。
5. **決済および入金の記録は Square 社の記録を正**とします。本システムに表示・集計される金額と Square の記録に差異がある場合、Square の記録が優先し、提供者は当該差異について責任を負いません。
6. **最終的な売上・納税額の確定は、顧客および顧客の税理士の責任において行うもの**とし、提供者は本システムの数値に起因する税務上の不利益について責任を負いません。

### 第◯条（責任の制限）

1. 提供者が顧客に対して負う損害賠償責任の総額は、**顧客が提供者に支払った本システムの対価の総額を上限**とします。
2. 提供者は、逸失利益、事業機会の喪失、データの喪失、営業の中断その他の**間接損害・特別損害について責任を負いません**（提供者がその可能性を知らされていた場合も同様）。
3. 前2項は、提供者の**故意または重大な過失**による場合には適用しません。

> **注意** — 第3項は必ず入れてください。故意・重過失まで免責する条項は無効と判断される可能性が高く、条項全体の有効性を損なうおそれがあります。

### 第◯条（不可抗力）

天災、疫病、戦争、法令の改廃、電気・通信の途絶、第三者サービスの停止その他当事者の合理的な支配を超える事由により債務を履行できない場合、当該当事者は責任を負いません。

### 第◯条（個人情報・顧客情報）

1. 本システムでは、顧客が伝票に入力した**来店客の氏名等**が記録されます。
2. 当該情報の取得・利用にあたっての本人への説明および同意取得は、**顧客の責任**とします。
3. 提供者は、システムの運用・保守に必要な範囲で当該情報にアクセスすることがあります。
4. 提供者は、当該情報を運用・保守以外の目的で利用せず、第三者に開示しません。

> 顧客名の入力欄がある以上、個人情報を扱うシステムです。委託先としての安全管理措置の取り決め（個人情報保護法の委託先監督）が必要かどうか、専門家に確認してください。

### 第◯条（契約終了時の措置）

1. 契約終了時、提供者は顧客の求めに応じ、**顧客のデータを汎用的な形式（CSV 等）で1回に限り無償で提供**します。
2. 前項のデータ提供後 ◯日を経過した時点で、提供者は顧客のデータおよび実行環境を削除できるものとします。
3. 削除後のデータ復元には応じられません。

### 第◯条（禁止事項）

顧客は、本システムについて、リバースエンジニアリング、第三者への再許諾・転売、提供者の許可なき複製・改変を行ってはなりません。

## 3. 技術的な残存リスクと、その扱い

### 3-0. 実施済みの対策 — 台帳の保護（`20260814_ledger_guard.sql`）

匿名キーはブラウザに配布される公開値のため、アプリ側の制御だけでは改ざんを防げません。**データベース側で**以下を強制しています。

| 操作 | 結果 |
|------|------|
| 確定した会計の**削除** | **不可**（保守用バイパス時のみ可） |
| 確定した会計の**金額・日付・人数の変更** | **不可**（変更できるのは取消・同期状態・備考のみ。トリガーで拒否） |
| 会計の**取消** | 会計から **7日以内**のみ。取消済みを元に戻すことも不可 |
| **過去日付の会計の追加** | **不可**（記録時刻の±15分以内、かつ現在の営業日ぶんのみ受け付ける） |
| **経費の追加・変更** | **当日の営業日ぶんのみ**（過去日への差し込み・二重計上を防止） |
| 伝票（明細）の**削除** | **不可** |

営業日の判定は店舗ごとの営業開始時刻に基づき、アプリの `getBusinessDate` と同じ規則を DB 関数 `current_business_date()` に置いています。深夜営業で暦日をまたぐ会計（実績で全体の約27%）も正しく通ります。

**残る余地** — 直近7日以内の会計の取消のみです。これは正規の訂正機能であり、取消は削除ではなく `canceled_at` として記録が残ります。

### 3-A. 受容すると判断したリスク（顧客への説明が必要）

以下は**改修せずに販売する**方針です。**顧客に説明しないまま販売すると後で問題になり得る**ため、契約書または納品時の説明資料に残してください。

#### ① 匿名キーを持つ者は当日ぶんのデータを操作できる

全テーブルの行レベルセキュリティが `anon` に対して全許可です（`supabase/migrations/20260722_rebuild.sql:103-110`）。

```sql
CREATE POLICY anon_all ON payments FOR ALL TO anon USING (true) WITH CHECK (true);
```

`NEXT_PUBLIC_SUPABASE_ANON_KEY` は**仕様上ブラウザに配布される公開値**で、開発者ツールから取得できます。秘匿できる種類の値ではないため、PIN を初期値から変更してもこの経路は塞がりません。

- 顧客ごとにプロジェクトを分けるため、**他社に見られる問題は発生しません**
- 一方、同一顧客内では**多店舗間で相互にデータを閲覧できます**
- 3-0 の対策により、**過去の売上の消去・改変・捏造は塞がりました**。残るのは当日ぶんの操作と、7日以内の取消です

**方針**: 当日ぶんの操作は正規の会計機能と区別できないため、店舗運営側の管理に委ねる。

#### ② PIN はソルト無しの SHA-256

`lib/pin.ts` は SHA-256 でハッシュ化するのみです。4〜6桁の数字は最大100万通りのため、ハッシュ値が入手されれば逆算できます。

**方針**: PIN は店舗内で共有する入店キーであり外部に配布しない前提とし、**納品時に初期値から任意の値へ変更してもらう**運用で対応する。

#### ③ 権限区分がない

ログインすると全員が「日計・管理」タブに入れます。売上の閲覧、商品マスタの変更、PIN の変更が誰でも可能です。会計取消に理由入力も承認もありません（ただし7日以内に限られ、取消の記録は残ります）。

**方針**: 店舗運営側の内部統制の問題として扱い、システムでは制御しない。

> **注意 — 「スプレッドシートに残るから改ざんは検知できる」は成立しません。**
> `gas/sync.gs` の `rebuildAnnualSheet()` は、同期のたびに**その年のシートを Supabase の内容で全再構築**します。POS 側のデータが書き換われば、スプレッドシートの過去の行も書き換わり、削除された会計は行ごと消えます。記録されるのは日次集計（日付・来客数・売上・現金・キャッシュレス・割引・経費・利益）のみで、明細は入りません。
> 改ざんの証跡として使うのであれば、**同期のたびにシートの複製を別途保存する**（Google Drive の版管理、または月次でPDF化）等の運用が別に必要です。閲覧権限の限定だけでは、元データの書き換えを防げません。

### 3-B. 直すか、契約書に書くか判断が必要

| # | 課題 | 現状 | 対応の方向 |
|---|------|------|-----------|
| 3-4 | データのエクスポート手段 | 画面上に CSV 出力機能がない。スプレッドシート同期は**日次集計のみ**で、明細は出ない | 契約終了時のデータ返還を約束するなら、明細のエクスポート機能が要る。**PayPay 分の復元手段が他に無い**点にも影響 |
| 3-5 | バックアップ | Supabase のプラン依存。無料・低位プランでは PITR（時点復旧）が使えない | データ消失時は Square 履歴からの再入力を前提とする方針のため、条文（第◯条）では**バックアップを約束しない**書き方に統一済み |
| 3-6 | 変更履歴 | 会計取消は `canceled_at` で残るが、**商品価格の改定履歴・オーダーの編集履歴は残らない** | 帳簿の証跡として説明できる範囲を把握しておく |
| 3-7 | インボイス・レシート | 適格請求書の発行機能なし。レシート印刷なし | 免責に明記（第◯条 会計・税務 に記載済み） |
| 3-8 | 消費税の端数処理 | `Math.round` 固定。切り捨て・切り上げを選べない | 顧客の経理方針と合うか確認。合わない場合は改修 |
| 3-9 | 認証情報の管理 | Square アクセストークン・GAS シークレットを環境変数で保持 | 顧客ごとに分離する運用手順を文書化する（4章のチェックリスト） |

### 3-C. 把握しておけばよい

- **Open-Meteo 依存** — 日報の天気は無料 API に依存。停止しても売上機能に影響はないが、日報の一部が欠ける
- **Square POS アプリ切替方式** — Square アプリの仕様変更で連携が壊れる可能性がある。復旧手順（未処理決済の照合）は実装済み
- **GAS のタイマートリガー** — Google 側の実行回数制限・認証切れで同期が止まることがある
- **ブラウザの localStorage 依存** — 端末のストレージ削除で未同期データが失われうる

## 4. 納品時チェックリスト（顧客ごとの環境分離）

顧客ごとに環境を分ける運用にするため、納品のたびに以下を実施します。手順書として運用してください。

- [ ] 顧客専用の Supabase プロジェクトを作成（**既存プロジェクトを使い回さない**）
- [ ] マイグレーション（`supabase/migrations/`）を順に適用
- [ ] 店舗マスタ（`stores`）を登録し、初期 PIN を設定

## 5. 弁護士に確認したい論点

契約書レビューを依頼する際、以下を質問事項として渡すと話が早く進みます。

1. **「買い切り」と表示しつつ運用が継続する形態**で、運用義務の終期（◯か月前通知での終了権）をどう定めるのが安全か
2. **テスト期間1か月で不具合対応を打ち切る**建て付けが、契約不適合責任との関係で有効か。期間経過後に重大な不具合が判明した場合にどこまで免責されるか
3. 責任上限を「受領済み対価の総額」とすることの妥当性（事業者間契約における有効性）
4. **本システムの数値に起因する税務上の不利益**について、免責がどこまで有効か
5. 来店客の氏名を扱うことについて、**個人情報保護法上の委託関係**の整理と必要な取り決め
6. データ消失時の復旧を **Square 履歴からの再入力に委ねる**建て付けについて、復元できない範囲（PayPay・明細・経費）を明記すれば免責が成立するか
7. 3-A の残存リスク（匿名キーによるデータ改変が可能である点）について、**契約書での開示・免責でどこまで処理できるか**。また、開示せずに販売した場合にどのようなリスクがあるか
